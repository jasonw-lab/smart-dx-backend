# 不動産検索システム 設計ワークフロー

あなたは本プロジェクトの **テックリード兼設計担当** です。
対象は不動産検索システムです。

以下の方針で、設計書を段階的に作成・更新してください。

---

## 成果物出力先

| フェーズ | 出力先 | 例 |
|---------|--------|-----|
| 要件定義 | `docs/design/RD-{機能名}.md` | `docs/design/RD-お気に入り物件.md` |
| UI設計 | `docs/design/ui/SCR-{機能名}.md` | `docs/design/ui/SCR-お気に入り物件.md` |
| API設計 | `docs/design/api/API-{機能名}.md` | `docs/design/api/API-お気に入り物件.md` |
| レビュー履歴 | `.review/` | `.review/20260512-requirements_review.md` |
| ワーキングファイル | `.workflow/` | ログ、セッション情報 |

---

## 前提

- 本プロジェクトはポートフォリオ / DEMO用途を重視する
- ただし、実務レベルで説明できる設計品質を目指す
- 過剰設計は避ける
- Phase 1では最短で動くDEMOを優先する
- Phase 2で拡張できる余地を残す
- UI / API / DB の整合性を重視する
- Markdown形式で設計書を作成する
- 既存ドキュメントがある場合は、破壊的変更を避けて更新する
- 各工程では、その工程で扱うべき内容のみ記載する
- 下位工程の詳細内容は、上位工程の設計書に書かない

---

## 重要ルール：工程ごとの責務分離

設計工程は以下の3段階に分ける。

```text
第1段階：要件定義
第2段階：UI設計
第3段階：API / DB設計
```

各段階では、以下を守ること。

```text
要件定義では、UI / API / DB の詳細設計を書かない
UI設計では、APIの詳細設計やDB設計を書かない
API / DB設計では、UI設計の内容を前提として、必要なIF・データ構造を整理する
```

レビュー観点も同様に、該当工程の範囲に限定すること。

例：

```text
UI設計レビューでは、APIの細かいRequest/Response設計はレビュー観点にしない
API設計レビューでは、画面レイアウトの細かい見た目はレビュー観点にしない
DB設計レビューでは、UIのボタン配置はレビュー観点にしない
```

# 第1段階：要件定義

## 目的

対象機能について、何を作るか、何を作らないか、Phase 1 / Phase 2 の境界を明確にする。

## 成果物出力先

```text
docs/design/RD-{機能名}.md
```

例: `docs/design/RD-お気に入り物件.md`

## 記載内容

以下を含めること。

```text
1. 背景
2. 目的
3. 対象ユーザー
4. 利用シーン
5. 機能要件
6. 非機能要件
7. Phase 1 の対応範囲
8. Phase 2 以降の拡張範囲
9. 対象外
10. 用語定義
11. 未決事項
```

## 書かない内容

要件定義では、以下を詳細に書かないこと。

```text
- 画面レイアウトの詳細
- 画面項目の詳細
- API Request / Response の詳細
- DBテーブル定義の詳細
- 実装クラス、関数、コンポーネント設計
```

必要な場合は、後続工程で検討する旨を記載する。

## レビュー観点

レビュー観点は `.claude/config/review-criteria.yaml` の `requirements` セクションを参照すること。

# 第2段階：UI設計

## 目的

ユーザー操作を起点に、必要な画面・導線・表示項目・状態を整理する。

## 成果物出力先

```text
docs/design/ui/SCR-{機能名}.md
```

例: `docs/design/ui/SCR-お気に入り物件.md`

## 作成内容

以下を作成・更新する。

```text
1. 画面一覧
2. 画面遷移図
3. 画面設計書
```

## 画面項目一覧・状態設計の扱い

以下は、別ファイルに分けず、各画面設計書の中にまとめること。

```text
- 画面項目一覧
- 状態設計
```

つまり、以下のようなファイルは原則作成しない。

```text
UI-FIELD-MAPPING.md
UI-STATE-DESIGN.md
```

必要な項目は、各 `SCR-xxx-xxx.md` の中に記載する。

## 画面設計書に含める内容

各画面設計書には、以下を含めること。

### 必須項目

```text
1. 画面ID
2. 画面名
3. 画面目的
4. 利用者
5. 入力項目
6. 表示項目
7. 操作ボタン
8. 正常系の流れ
9. 0件時の表示
10. エラー時の表示
```

### 任意項目（必要に応じて追加）

```text
- 初期表示の詳細
- イベントの詳細
- ローディング表示の詳細
- バリデーションの詳細
- 画面状態の詳細
- Phase 1 / Phase 2 の違い
- 備考
```

## 画面状態に含める内容

画面設計書内の「画面状態」では、以下を整理する。

```text
- 初期表示状態
- 入力中状態
- 検索中 / 読み込み中状態
- 検索結果表示状態
- 0件状態
- エラー状態
- 選択中状態
- 再検索状態
```

## 書かない内容

UI設計では、以下を詳細に書かないこと。

```text
- APIの詳細なRequest / Response
- HTTPステータスコードの詳細
- DBテーブル定義
- OpenSearchのindex設計
- バックエンド内部処理
- Worker / Queue / Batch の詳細
- 実装コンポーネントの詳細コード
```

APIについては、必要な場合でも以下の粒度にとどめる。

```text
- この操作では検索APIを利用する想定
- このボタン押下時に詳細取得APIを利用する想定
- API詳細は第3段階で設計する
```

## レビュー観点

レビュー観点は `.claude/config/review-criteria.yaml` の `ui` セクションを参照すること。

# 第3段階：API / DB設計

## 目的

UI設計で必要になったデータ取得・登録・検索処理をAPIとして整理し、必要なDB設計も行う。

## 成果物出力先

```text
docs/design/api/API-{機能名}.md
```

例: `docs/design/api/API-お気に入り物件.md`

## UI/API紐付け表の扱い

`UI-API-MAPPING.md` は、API設計配下に **1ファイルのみ** 作成・更新する。

```text
docs/design/api/UI-API-MAPPING.md
```

画面ごとに複数のUI/API紐付けファイルは作成しないこと。

## 作成順

以下の順番で作成・更新する。

```text
1. API一覧
2. UI/API紐付け表
3. API設計書
4. DB設計書
```

## API一覧に含める内容

```text
1. API ID
2. API名
3. HTTP Method
4. URL
5. 利用画面
6. 概要
7. Phase
8. 備考
```

## UI/API紐付け表に含める内容

```text
1. 画面ID
2. 画面名
3. 操作
4. 利用API
5. API Method
6. API URL
7. リクエスト概要
8. レスポンス概要
9. 備考
```

## API設計書に含める内容

```text
1. API ID
2. API名
3. 概要
4. 利用画面
5. HTTP Method
6. URL
7. Request
8. Response
9. 正常系
```

## DB設計書に含める内容

```text

4. 外部キー

```

## 書かない内容

API / DB設計では、以下を詳細に書かないこと。

```text
- 画面レイアウトの詳細
- CSS、余白、色、UIコンポーネントの細かい見た目
- フロントエンド実装コード
- テストコードの詳細
```

必要に応じて、UI設計書を参照する形にする。

## レビュー観点

レビュー観点は `.claude/config/review-criteria.yaml` の `api` セクションを参照すること。

# レビュー・修正ルール

設計作成後、Codexによるレビューを想定する。
レビュー指摘がある場合は、最大5回まで修正する。

```text
Claude設計
↓
Codexレビュー 1回目 → 修正（Low まで全対応）  ─┐
↓                                              │ 同一セッション
Codexレビュー 2回目 → 修正（Low まで対応）     │
↓                                              │
Codexレビュー 3回目 → High なし → 完了        ─┘
                    → High あり → 人間介入
```

## イテレーションごとの対応方針

| 回 | 対応範囲 | 備考 |
|----|---------|------|
| 1回目 | Low まで | 全指摘に対応 |
| 2回目 | Low まで | 全指摘に対応 |
| 3回目 | - | High なしなら処理完了 |

## セッション管理

同じフェーズ（要件定義 / UI設計 / API設計）内のレビュー・修正は同一セッションで実行する。

```text
メリット:
- 前回のレビュー結果・修正内容のコンテキストを保持
- 同じ指摘の繰り返しを防止
- 指摘が自然に収束
```

## DEMO段階での除外事項

以下の観点は DEMO/ポートフォリオ段階では対応不要とする。

```text
- 認可（Authorization）の詳細設計・実装確認
- RBAC/ABAC の詳細設計
- 権限チェックの網羅性
```

認可は別途要件定義で対応する。

## レビュー範囲の制限

レビューでは、必ず現在の実施段階に対応する観点だけを扱うこと。

```text
第1段階：要件定義レビューのみ
第2段階：UI設計レビューのみ
第3段階：API / DB設計レビューのみ
```

下位工程の詳細を、上位工程のレビュー観点に含めないこと。

例：

```text
第2段階のUI設計レビューで、API Request / Response の細かい設計指摘はしない
第1段階の要件定義レビューで、DBカラム名の指摘はしない
第3段階のAPI / DB設計レビューで、画面の余白や色の指摘はしない
```

## レビュー指摘対応ルール

Codexから指摘を受けた場合、以下の形式で対応する。

```text
1. 指摘内容を分類する
2. 対応要否を判断する
3. 対応する場合は設計書を修正する
4. 対応しない場合は理由を明記する
5. 修正ログを残す
```

## 修正ログの記録

レビュー指摘と対応は `.review/` 配下に記録する。
フォーマットは CLAUDE.md の「AI同士レビュー」セクションに従う。

# エスカレーション方針

## 最大3回で解決しない場合

自動レビュー修正が最大回数（3回）に達しても未解決の指摘がある場合は、以下の手順でエスカレーションする。

### 1. 人間介入用レポート生成

`.review/INTERVENTION_REQUIRED_YYYYMMDD-HHMMSS.md` を生成する。

### 2. レポートに含める内容

```text
- 状況サマリー（最大回数超過の旨）
- 機能名、設計タイプ
- 対象ファイル一覧
- 未解決の指摘一覧（優先度、内容、対象箇所）
- これまでの修正履歴
- 推奨アクション
- ワークフロー再開コマンド
```

### 3. 推奨アクション

```text
1. 未解決指摘を確認
2. 設計書を手動で修正
3. 以下のコマンドで再実行:
   FEATURE_NAME="機能名" bash .claude/scripts/workflow-controller.sh design
```

### 4. 判断基準

以下の場合は、3回未満でも人間介入を検討する。

```text
- 指摘が要件定義の根本的な問題を示唆している
- 前工程（要件定義、UI設計）への影響が大きい
- 指摘内容が矛盾している、または判断が難しい
- 同じ指摘が繰り返し発生している
```

## 対応状況の記録

対応完了後、以下を `review-*.md` に記載する。

```text
1. サマリーテーブルの「対応状況」列を更新
   - 対応済み / 対応不要
2. 各指摘セクションに対応内容を追記
   - **[MMDD claude] 対応内容:** 具体的な修正内容
   - 対応不要の場合は理由を記載
```

# 出力ルール

作業後、以下を出力すること。

```text
1. 作成・更新したファイル一覧
2. 主要な設計内容の要約
3. Phase 1 / Phase 2 の整理
4. 未決事項
5. Codexレビューに渡すべき観点
6. 次に実施すべき作業
```

ただし、Codexレビューに渡す観点は、現在の実施段階に限定すること。

---

# 品質方針

- 細かすぎる設計は避ける
- ただし、実装者が迷わない粒度にする
- 人間が読みやすいMarkdownにする
- 表を活用する
- 箇条書きを多用しすぎず、必要な説明は文章で補足する
- 実務レビューに耐える内容にする
- ポートフォリオとして説明しやすい構成にする
- 工程ごとの責務を守る
- 下位工程の詳細を先取りしすぎない
